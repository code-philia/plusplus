01 · Multimodal input

One requirement, two kinds of evidence

REQ-1.1 · Register a traveler account

A visitor provides nationality, identity and credential fields, accepts the terms, and submits the registration form. Inputs must satisfy the specified validity rules, and username and email must be unused. A valid submission persists the account, establishes a signed-in session, and returns home; invalid or duplicate input must create neither account nor session.

The requirement scenarios distinguish successful registration from invalid or duplicate submissions. The image contributes layout and control evidence, not business rules.

02 · Compilation path

Architecture is progressively constrained

The compiler does not ask one model call to invent the whole application. It carries requirement-derived data and interface obligations forward; each representation narrows the choices available to subsequent passes.

The order shown follows the artifacts in smoke-1; implementation fills requirement-owned source bodies after lowering.

Model-local decisions. Interpret requirement semantics and image cues; propose requirement-scoped records or edits.

Compiler-owned structure. Merge records, preserve traceability, bind references and contracts, and map modules to deterministic files.

03 · Database schema

Persistent concepts become a canonical vocabulary

The schema pass turns account creation and session persistence into explicit entities, fields, and a relationship. This vocabulary is then reused by backend inputs, effects, and storage operations.

Representative schema (abbreviated)

Account(
  id                       UUID PRIMARY KEY,
  name, nationality,
  passport_number,
  passport_expiration_date,
  date_of_birth, gender,
  username, email, password
)

Session(
  id                       UUID PRIMARY KEY,
  account_id               FK → Account.id UNIQUE
)

Account 1 ─── 1 Session

Requirement-derived fields. The account contains traveler identity, credential, and contact data. Requiredness and field descriptions are recorded in the schema.

Relationship. A session is linked to its account by a required foreign key; the one-to-one relationship is represented by uniqueness on Session.account_id.

Behavioral constraint. Registration checks username and case-insensitive email before insertion. The backend IR expresses these lookup obligations instead of treating uniqueness as a UI-only concern.

System-generated IDs and field types complete the persistent record shape. This excerpt omits the full field metadata and non-null constraints.

04 · Backend IR

An API contract resolves into a call and data-flow graph

Requirement-level obligation

Valid registration
  → persist traveler account
  → create signed-in session
  → return account identity

Invalid or duplicate input
  → return an error
  → persist neither record

Explicit API boundary from modules_api.json

POST /api/register-traveler-account

Request:
  traveler fields + credentials
  + password confirmation
  + terms_accepted

Response:
  account_id: UUID
  username: string
  session_id: UUID

Decomposition recorded in the IR. API.RegisterTravelerAccount calls FUNC.ValidateRegistrationInput (pure validation), FUNC.CheckDuplicateCredentials (backed by DB.ReadAccountCredentials), FUNC.PersistTravelerAccount (backed by DB.InsertAccountRecord), and FUNC.EstablishSignedInSession (backed by DB.PersistSessionRecord and session-cookie writing). The outputs account_id, username, and session_id form the API response contract.

05 · Frontend IR

The UI tree and interaction contract are separate, then connected

The frontend pass traverses requirements in three rounds: first it records requirement-linked UI and data; next it assembles and reuses components; finally it attaches component state and behavior. For this requirement, the screenshot informs the page composition while the text supplies fields, validation, and submit outcomes.

06 · Cross-stack flow

07 · Lowering and implementation

Lowering fixes ownership and interfaces before bodies are completed

The code-binding registry maps IR entities to stable source locations and symbols. Lowering emits files, types, module shells, imports, and wiring from those bindings; implementation then fills the designated source bodies without reopening the architecture at repository scale.

What this artifact does and does not show

The backend handler source shows the API calling the declared validation, duplicate-check, persistence, and session modules. In contrast, the captured RegisterPage.tsx is still a typed lowering shell: it declares component state and an effect runner, but its return remains an empty fragment pending UI implementation.

Therefore, smoke-1 demonstrates the IR-to-file allocation and explicit contracts; it is not evidence that this snapshot already reproduces the reference page or completes registration end to end.

08 · Draftable example prose

A compact paragraph for the paper

Consider the traveler-registration requirement, which combines field-level validation and persistent account creation with a reference image of the registration page. The schema pass identifies the Account and Session entities and their one-to-one relationship. The backend IR then specifies a registration API with typed inputs and outputs, and decomposes its obligations into validation, duplicate-credential lookup, account persistence, and session establishment. The frontend IR records the registration UI and its data, assembles the page from a reusable header and a form component, and represents submission as a UI event handled by a component-scoped handler that invokes a request effect targeting the registration API. The response is propagated as a success event to the application component, which updates the signed-in identity and returns to the home page. Deterministic lowering binds these records to source files and shared contracts, leaving implementation to complete bounded module bodies rather than to redesign the cross-stack architecture.
